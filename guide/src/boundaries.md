# ขอบเขตการไบเซกต์

`cargo-bisect-rustc` ทำการค้นหาแบบไบนารีหารีเกรสชันโดยใช้ขอบเขต *start* และ *end*
คุณสามารถระบุขอบเขตเหล่านี้ได้ด้วยตัวเลือก CLI `--start` และ `--end`
มีหลายวิธีในการระบุว่าขอบเขตเหล่านั้นคืออะไร
หากคุณรันคำสั่งโดยไม่ระบุขอบเขต มันจะค้นหาให้โดยอัตโนมัติ:

```sh
# No --start or --end flags
cargo bisect-rustc
```

วิธีนี้จะถือว่า nightly ล่าสุดคือรีเกรสชัน (ขอบเขต *end*)
จากนั้นจะค้นหาย้อนหลังไปเรื่อย ๆ จนกว่าจะพบ nightly ที่ผ่าน เพื่อใช้เป็นขอบเขต *start*
การไบเซกต์มักจะเร็วกว่าได้ถ้าคุณบังเอิญรู้ขอบเขต start เพราะไม่ต้องค้นหาให้

`--start` และ `--end` เป็นตัวเลือกเสริม
หากไม่ได้ระบุ `--start` มันจะพยายามหาช่วง start โดยอัตโนมัติ
หากไม่ได้ระบุ `--end` มันจะถือว่าเป็นเวอร์ชันล่าสุดที่มีอยู่

## ขอบเขตแบบวันที่

คุณสามารถส่งวันที่ในรูปแบบ YYYY-MM-DD ให้กับตัวเลือก `--start` และ `--end`
เครื่องมือจะดาวน์โหลด nightly ที่ตรงกับวันที่นั้น แล้วเริ่มไบเซกต์ nightly เหล่านั้น

```sh
cargo bisect-rustc --start=2018-08-14 --end=2018-10-11
```

ถ้า nightly ที่มีรีเกรสชันอยู่ในช่วง 167 วันที่ผ่านมา มันจะเริ่มไบเซกต์ PR แต่ละตัวที่ถูก merge ในวันนั้นโดยอัตโนมัติ โดยใช้ [ขอบเขตแบบ git commit](#ขอบเขตแบบ-git-commit)

> **หมายเหตุ**: กับดักอย่างหนึ่งคือ ถ้าคุณใช้คำสั่งเช่น `rustc +nightly --version` เพื่อดูเวอร์ชันที่คุณใช้อยู่ มันมักจะระบุวันที่ที่เร็วกว่าเวอร์ชันทูลเชน nightly หนึ่งวัน เช่น `nightly-2025-07-19` จะบอกว่า `2025-07-18` เพราะนั่นคือตอนที่คอมมิตล่าสุดถูก merge แม้ว่าทูลเชนจะเผยแพร่ในวันที่ 19 ก็ตาม

## ขอบเขตแบบ git commit

คุณสามารถส่ง git commit hash เฉพาะของ PR เป็นขอบเขตได้
โปรเจกต์ Rust เก็บบิลด์ของ PR ที่ถูก merge ทุกตัวในช่วง 167 วันล่าสุด
ถ้าคุณบังเอิญรู้ PR ที่จะใช้เป็นขอบเขต คุณสามารถส่ง SHA-1 hash ของ PR นั้นได้

```sh
cargo bisect-rustc \
    --start=6323d9a45bdf0ac2a9319a6a558537e0a7e6abd1 \
    --end=866a713258915e6cbb212d135f751a6a8c9e1c0a
```

มีหลายวิธีในการหา SHA-1 hash ของ PR

- บนหน้า PR เอง คุณควรเห็นข้อความประมาณว่า "bors merged commit c50c62d into `rust-lang:<default-branch>`"
  คุณสามารถคัดลอก hash นั้นมาใช้เป็นขอบเขตได้
  ถ้า PR ถูก merge เป็นส่วนหนึ่งของโรลอัป คุณจะต้องใช้ hash ของโรลอัปแทน
  คุณจะต้องไล่ดูข้อความใน PR เพื่อดูว่า PR ถูกกล่าวถึงจากโรลอัป PR หรือไม่
- ในรีโพสิทอรี rust ให้รัน `git log --first-parent upstream/HEAD` (โดยที่ `upstream` คือชื่อ origin ของคุณสำหรับ `rust-lang/rust`)
  คำสั่งนี้จะแสดงคอมมิตระดับบนสุดทั้งหมด
  จากนั้นคุณสามารถค้นหา PR ของคุณได้

> **หมายเหตุ**: ถ้า PR ถูก merge หลังจาก nightly ล่าสุด คุณต้องระบุช่วง `--end` ด้วย
> มิฉะนั้นมันจะถือว่า nightly ล่าสุดคือ *end* และจะใช้งานไม่ได้ถ้า start อยู่หลัง end

ถ้าพบรีเกรสชันใน [โรลอัป PR] `cargo-bisect-rustc` จะไบเซกต์ PR แต่ละตัวภายในโรลอัปนั้น
การไบเซกต์ขั้นสุดท้ายนี้ใช้ได้เฉพาะ `x86_64-unknown-linux-gnu` เพราะใช้บิลด์ที่สร้างสำหรับ [ตัวติดตามประสิทธิภาพของ rustc]

> **หมายเหตุ**: ถ้าคุณระบุขอบเขตแบบวันที่ คุณสามารถใช้ตัวเลือก CLI `--by-commit` เพื่อบังคับให้ใช้ PR commits แทน nightly

[โรลอัป PR]: https://forge.rust-lang.org/release/rollups.html
[ตัวติดตามประสิทธิภาพของ rustc]: https://perf.rust-lang.org/

## ขอบเขตแบบ git tag

ขอบเขตสามารถระบุได้ด้วย git release tag
วิธีนี้มีประโยชน์ถ้าคุณรู้ว่าบางอย่างทำงานในรีลีสหนึ่งแต่ไม่ทำงานในอีกรีลีสหนึ่ง แต่คุณไม่รู้ว่า nightly ตัวไหนที่ตรงกับรีลีสนั้น
เมื่อได้รับ tag `cargo-bisect-rustc` จะพยายามหา nightly ที่ตรงกับรีลีสนั้น ตัวอย่างเช่น:

```sh
cargo bisect-rustc --start=1.58.0 --end=1.59.0
```

## ความเป็นโมโนโทนิก

เมื่อเขียนการทดสอบและเลือกช่วงการไบเซกต์ คุณควรระวังให้แน่ใจว่าการทดสอบจะไม่เปลี่ยนผ่าน/ล้มเหลวไปมาระหว่างช่วงการไบเซกต์
มันควรเปลี่ยนจากดีไปแย่เพียงครั้งเดียวในช่วงการไบเซกต์ (มันต้องเปลี่ยนแบบ [โมโนโทนิก])

ในตัวอย่างต่อไปนี้ `cargo-bisect-rustc` จะพบการเปลี่ยนแปลงจุดหนึ่ง แต่จุดนั้นอาจไม่ใช่สาเหตุที่แท้จริงของปัญหาที่คุณกำลังสืบสวน

```text
nightly-2023-02-01 baseline **start**
nightly-2023-02-02 baseline
nightly-2023-02-03 baseline
nightly-2023-02-04 regression
nightly-2023-02-05 regression
nightly-2023-02-06 baseline
nightly-2023-02-07 regression
nightly-2023-02-08 regression **end**
```

ในกรณีนี้มันอาจพบว่า 2023-02-04 หรือ 2023-02-07 เป็นรีเกรสชันก็ได้

ต่อไปนี้เป็นคำแนะนำบางอย่างในการหลีกเลี่ยงหรือจัดการกับปัญหานี้:

- ตรวจสอบให้แน่ใจว่าการทดสอบของคุณแสดงปัญหาที่คุณกำลังหาอย่างน่าเชื่อถือ และไม่สร้างผลบวกลวงหรือผลลบลวง
- วิเคราะห์ PR ที่ถูกระบุว่าเป็นรีเกรสชัน
  การเปลี่ยนแปลงใน PR ดูเหมือนจะเป็นสาเหตุที่น่าจะเป็นไปได้ไหม?
- พยายามทำให้ช่วงการไบเซกต์เล็ก เพื่อลดความน่าจะเป็นที่จะเจอการเปลี่ยนผ่านหลายจุด
- ใช้ตัวเลือก `-vv` (verbose มาก) เพื่อแสดงผลลัพธ์จากคอมไพเลอร์และให้แน่ใจว่าเป็นสิ่งที่คุณคาดหวัง
- ใช้ตัวเลือก [`--prompt`](tutorial.md#การทดสอบแบบอินเทอรแอกทีฟ) เพื่อตรวจสอบผลลัพธ์และยืนยันในแต่ละขั้นตอน
- ระวังว่าบางปัญหาอาจถูกแก้ไขแล้วกลับมาเกิดรีเกรสชันอีกหลายครั้ง
  พยายามให้ช่วงการไบเซกต์อยู่ใกล้กับปัจจุบันมากที่สุด
  เปรียบเทียบผลลัพธ์ของคอมมิตที่ "เกิดรีเกรสชัน" กับ nightly ล่าสุดเพื่อดูว่าเหมือนกันหรือไม่
- ถ้าการทดสอบล้มเหลวเป็นครั้งคราวเท่านั้น ให้ใช้ [สคริปต์](examples/flaky.md) เพื่อรันคอมไพเลอร์หลาย ๆ ครั้งจนกว่าจะล้มเหลว หรือจนกว่าจะผ่านพอหลายรอบจนคุณมั่นใจว่ามันดี
- ถ้าโค้ดต้องใช้ฟีเจอร์ภาษาที่ค่อนข้างใหม่ ระวังอย่าเลือกช่วงเริ่มต้นที่เก่าเกินไป
- ระวังบั๊กที่เกี่ยวกับการสร้างโค้ด (code-generation) ซึ่งอาจไวต่อเค้าโครงของโค้ด
  เนื่องจากโค้ดของ rustc เปลี่ยนแปลงอย่างรวดเร็วตลอดเวลา โค้ดจึงขยับไปมาได้ ทำให้เค้าโครงและการปรับแต่งประสิทธิภาพต่างกัน ซึ่งอาจทำให้ปัญหาเกิดขึ้นและหายไปหลายครั้งตลอดช่วงการไบเซกต์

[โมโนโทนิก]: https://en.wikipedia.org/wiki/Bisection_(software_engineering)#Monotonicity
