# ขอบเขตการไบเซกต์

`cargo-bisect-rustc` อาศัยการค้นหาแบบไบนารีเพื่อระบุจุดที่เกิดรีเกรสชัน โดยใช้ขอบเขตเริ่มต้น (*start*) และขอบเขตสิ้นสุด (*end*)
คุณสามารถระบุขอบเขตเหล่านี้ได้ผ่านตัวเลือก CLI `--start` และ `--end`
ซึ่งมีหลากหลายวิธีในการกำหนดค่าขอบเขตดังกล่าว
หากคุณสั่งรันคำสั่งโดยไม่ได้ระบุขอบเขต เครื่องมือจะพยายามค้นหาให้โดยอัตโนมัติ:

```sh
# No --start or --end flags
cargo bisect-rustc
```

ในกรณีนี้ เครื่องมือจะถือว่า nightly เวอร์ชันล่าสุดคือจุดที่เกิดรีเกรสชัน (ขอบเขต *end*)
จากนั้นจะค้นหาย้อนหลังไปเรื่อยๆ จนกว่าจะพบ nightly ที่บิลด์ผ่าน เพื่อนำมาใช้เป็นขอบเขต *start*
ทั้งนี้ การไบเซกต์จะทำได้รวดเร็วกว่ามากหากคุณทราบขอบเขต start ล่วงหน้าอยู่แล้ว เพราะช่วยตัดขั้นตอนการสแกนค้นหาออกไปได้

ตัวเลือก `--start` และ `--end` เป็นตัวเลือกเสริม (optional):
- หากไม่ได้ระบุ `--start` เครื่องมือจะพยายามค้นหาช่วงเริ่มต้นให้โดยอัตโนมัติ
- หากไม่ได้ระบุ `--end` เครื่องมือจะถือว่าเป็นเวอร์ชันล่าสุดที่มีให้ดาวน์โหลด

## ขอบเขตแบบวันที่

คุณสามารถส่งวันที่ในรูปแบบ YYYY-MM-DD ให้กับแฟล็ก `--start` และ `--end` ได้
เครื่องมือจะดาวน์โหลด nightly ที่ตรงกับวันดังกล่าว แล้วเริ่มต้นไบเซกต์ระหว่าง nightly เหล่านั้น

```sh
cargo bisect-rustc --start=2018-08-14 --end=2018-10-11
```

หาก nightly ที่พบรีเกรสชันอยู่ในช่วง 167 วันล่าสุด ระบบจะเริ่มไบเซกต์ย่อยระหว่างแต่ละ PR ที่ถูก merge ในวันนั้นโดยอัตโนมัติ โดยใช้ [ขอบเขตแบบ git commit](#ขอบเขตแบบ-git-commit)

> **หมายเหตุ**: ข้อพึงระวังคือ หากคุณใช้คำสั่งเช่น `rustc +nightly --version` เพื่อตรวจสอบเวอร์ชันที่ใช้งานอยู่ วันที่ที่แสดงมักจะเร็วกว่าวันที่ของเวอร์ชันทูลเชน nightly อยู่หนึ่งวัน ตัวอย่างเช่น `nightly-2025-07-19` จะแสดงวันที่เป็น `2025-07-18` เนื่องจากเป็นเวลาที่คอมมิตล่าสุดถูก merge เข้ามา แม้ว่าตัวทูลเชนจะเผยแพร่ในวันที่ 19 ก็ตาม

## ขอบเขตแบบ git commit

คุณสามารถระบุ git commit hash ของ PR ที่ต้องการเพื่อใช้เป็นขอบเขตได้
โดยปกติโปรเจกต์ Rust จะเก็บบิลด์ของทุก PR ที่ถูก merge ไว้เป็นเวลาย้อนหลัง 167 วัน
หากคุณทราบ PR ที่ต้องการใช้เป็นขอบเขตอยู่แล้ว คุณสามารถส่ง SHA-1 hash ของ PR นั้นเข้าไปได้โดยตรง:

```sh
cargo bisect-rustc \
    --start=6323d9a45bdf0ac2a9319a6a558537e0a7e6abd1 \
    --end=866a713258915e6cbb212d135f751a6a8c9e1c0a
```

การค้นหา SHA-1 hash ของ PR สามารถทำได้หลายวิธีดังนี้:

- บนหน้า PR ของ GitHub คุณจะเห็นข้อความทำนองว่า "bors merged commit c50c62d into `rust-lang:<default-branch>`"
  คุณสามารถคัดลอก commit hash นั้นมาใช้เป็นขอบเขตได้
  แต่หาก PR นั้นถูก merge เป็นส่วนหนึ่งของ rollup คุณจำเป็นต้องใช้ commit hash ของตัว rollup PR แทน โดยคุณสามารถตรวจดูข้อความใน PR เพื่อดูว่าถูกอ้างอิงจาก rollup PR ใด
- ในเครื่องของคุณที่โคลนรีโพสิทอรี rust ไว้ ให้สั่งรัน `git log --first-parent upstream/HEAD` (โดยที่ `upstream` คือ remote ที่ชี้ไปยัง `rust-lang/rust`)
  คำสั่งนี้จะแสดงคอมมิตระดับบนสุด (top-level merge commits) ทั้งหมด ซึ่งคุณสามารถค้นหา PR ที่ต้องการได้จากจุดนี้

> **หมายเหตุ**: หาก PR นั้นถูก merge หลังจากวันที่ของ nightly ล่าสุด คุณต้องระบุขอบเขต `--end` ด้วยเสมอ มิฉะนั้นระบบจะถือว่า nightly ล่าสุดคือจุด *end* ซึ่งจะทำงานผิดพลาดหากจุด start ดันเกิดขึ้นหลังจุด end

หากพบว่ารีเกรสชันอยู่ใน [โรลอัป PR] `cargo-bisect-rustc` จะทำการไบเซกต์ย่อยระหว่างแต่ละ PR ภายในโรลอัปนั้นให้
(การไบเซกต์ขั้นสุดท้ายนี้รองรับเฉพาะบน `x86_64-unknown-linux-gnu` เนื่องจากอาศัยบิลด์ที่สร้างขึ้นสำหรับ [ตัวติดตามประสิทธิภาพของ rustc])

> **หมายเหตุ**: หากคุณระบุขอบเขตเป็นวันที่ คุณสามารถใช้ตัวเลือก CLI `--by-commit` เพื่อบังคับให้ค้นหาตาม PR commit แทนที่จะใช้ nightly ได้

[โรลอัป PR]: https://forge.rust-lang.org/release/rollups.html
[ตัวติดตามประสิทธิภาพของ rustc]: https://perf.rust-lang.org/

## ขอบเขตแบบ git tag

คุณยังสามารถกำหนดขอบเขตด้วย release tag ของ git ได้อีกด้วย
วิธีนี้มีประโยชน์มากเมื่อคุณทราบว่าโค้ดทำงานได้ในเวอร์ชันหนึ่ง แต่เกิดปัญหาในอีกเวอร์ชันหนึ่ง ทว่าไม่ทราบว่าตรงกับ nightly ของวันใด
เมื่อระบุแท็กเข้ามา `cargo-bisect-rustc` จะค้นหา nightly ที่ตรงกับเวอร์ชัน release นั้นให้โดยอัตโนมัติ ตัวอย่างเช่น:

```sh
cargo bisect-rustc --start=1.58.0 --end=1.59.0
```

## ความเป็นโมโนโทนิก

ในการเขียนชุดทดสอบและเลือกช่วงการไบเซกต์ คุณควรระมัดระวังให้มั่นใจว่าผลการทดสอบจะไม่แกว่งสลับไปมาระหว่างผ่านกับล้มเหลว
โดยผลลัพธ์ควรเปลี่ยนจากสภาพดี (good) ไปเป็นมีปัญหา (bad) เพียงครั้งเดียวตลอดช่วงการไบเซกต์ (นั่นคือการเปลี่ยนแปลงต้องเป็นแบบ [โมโนโทนิก])

ในตัวอย่างต่อไปนี้ `cargo-bisect-rustc` จะตรวจพบจุดเปลี่ยนจุดใดจุดหนึ่ง แต่จุดนั้นอาจไม่ใช่สาเหตุที่แท้จริงของปัญหาที่คุณกำลังสืบสวน:

```text
nightly-2023-02-01 baseline **start**
nightly-2023-02-02 baseline
nightly-2023-02-03 baseline
nightly-2023-02-04 regression
nightly-2023-02-05 regression
nightly-2023-02-06 baseline
nightly-2023-02-07 regression
nightly-2023-02-08 regression **end**
```

จากข้อมูลข้างต้น เครื่องมืออาจรายงานว่าจุดที่เกิดรีเกรสชันคือ 2023-02-04 หรือ 2023-02-07 ก็เป็นได้

ข้อแนะนำเพื่อหลีกเลี่ยงหรือรับมือกับปัญหานี้ ได้แก่:

- ตรวจสอบให้แน่ใจว่าชุดทดสอบของคุณสามารถจำลองอาการปัญหาได้อย่างแม่นยำสม่ำเสมอ ไม่ก่อให้เกิดผลบวกลวง (false positive) หรือผลลบลวง (false negative)
- วิเคราะห์ PR ที่ถูกรายงานว่าเป็นต้นเหตุของรีเกรสชันอย่างละเอียด ว่าการแก้ไขโค้ดใน PR นั้นดูสมเหตุสมผลที่จะก่อให้เกิดปัญหาดังกล่าวหรือไม่
- พยายามจำกัดช่วงการไบเซกต์ให้แคบลง เพื่อลดโอกาสที่จะพบการเปลี่ยนสถานะซ้ำซ้อนหลายครั้ง
- ใช้แฟล็ก `-vv` (very verbose) เพื่อสั่งให้แสดง output จากคอมไพเลอร์อย่างละเอียด ช่วยให้มั่นใจว่าผลลัพธ์ตรงกับสิ่งที่คุณคาดไว้
- ใช้แฟล็ก [`--prompt`](tutorial.md#การทดสอบแบบอินเทอรแอกทีฟ) เพื่อตรวจสอบ output ด้วยตนเองและยืนยันผลในแต่ละขั้นตอน
- พึงระวังว่าบางปัญหาอาจได้รับการแก้ไขแล้ว แต่กลับมาเกิดซ้ำอีกหลายครั้ง ให้พยายามกำหนดช่วงการไบเซกต์ให้อยู่ใกล้กับช่วงเวลาปัจจุบันมากที่สุด และเปรียบเทียบผลลัพธ์ของคอมมิตที่เกิดปัญหาเข้ากับ nightly ล่าสุดว่ามีลักษณะเดียวกันหรือไม่
- หากชุดทดสอบล้มเหลวเพียงแค่บางครั้ง (sporadic failure) ให้ใช้ [สคริปต์](examples/flaky.md) สั่งรันคอมไพเลอร์ซ้ำหลายๆ รอบจนกว่าจะพบข้อผิดพลาด หรือจนกว่าจะผ่านการทดสอบมากพอจนคุณมั่นใจได้ว่ารอบนั้นไม่มีปัญหา
- หากโค้ดจำเป็นต้องใช้ฟีเจอร์ใหม่ของภาษา ควรระวังอย่าเลือกช่วงเริ่มต้น (start range) ที่เก่าเกินไป
- พึงระวังบั๊กประเภทสร้างโค้ด (code-generation bugs) ซึ่งอาจอ่อนไหวต่อการจัดวางเลย์เอาต์ของโค้ด เนื่องจากซอร์สโค้ดของ rustc มีการเปลี่ยนแปลงอย่างรวดเร็ว โค้ดอาจมีการขยับปรับเปลี่ยนจนส่งผลให้เลย์เอาต์และการทำ optimize ของคอมไพเลอร์แตกต่างกันไป ซึ่งอาจทำให้บั๊กโผล่ขึ้นมาแล้วหายไปสลับกันหลายครั้งตลอดช่วงการไบเซกต์

[โมโนโทนิก]: https://en.wikipedia.org/wiki/Bisection_(software_engineering)#Monotonicity
