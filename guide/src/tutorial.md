# บทช่วยสอน

หลักการทำงานของ `cargo-bisect-rustc` คือการบิลด์โปรเจกต์ Cargo และตรวจสอบว่าการบิลด์สำเร็จหรือล้มเหลว บทช่วยสอนนี้จะพาคุณดูตัวอย่างขั้นตอนการทำงานจริงตั้งแต่ต้นจนจบ

## การค้นหารีเกรสชัน

เริ่มต้นด้วยการสร้างโปรเจกต์ Cargo ขึ้นมาเพื่อจำลองปัญหารีเกรสชัน โดยในที่นี้จะขอยกตัวอย่างจาก [issue #53157]:

```sh
cargo new foo
cd foo
```

แก้ไขไฟล์ `src/main.rs` โดยใส่โค้ดตัวอย่างจาก issue ดังกล่าว:

```rust
macro_rules! m {
    () => {{
        fn f(_: impl Sized) {}
        f
    }}
}

fn main() {
    fn f() -> impl Sized {};
    m!()(f());
}
```

เนื่องจากกรณีนี้เป็นการทดสอบรีเกรสชันในอดีต ให้แก้ไขไฟล์ `Cargo.toml` โดยลบฟิลด์ `edition = "2021"` ออก เนื่องจากคอมไพเลอร์เวอร์ชันเก่ายังไม่รองรับ edition นี้

จากนั้นรันคำสั่ง `cargo bisect-rustc --end=2018-08-04`

สำหรับตัวอย่างนี้ เราจำเป็นต้องระบุจุดสิ้นสุด (`--end`) เพราะเป็นรีเกรสชันเก่าที่ได้รับการแก้ไขไปแล้วใน nightly เวอร์ชันล่าสุด นอกจากนี้ หากเราทราบจุดเริ่มต้น (`--start`) อยู่แล้ว ก็สามารถระบุเข้าไปด้วยได้ ซึ่งจะช่วยให้การทำงานเร็วขึ้นมากเพราะไม่ต้องเสียเวลาสแกนหาจุดเริ่มต้น ตัวอย่างเช่น:

```sh
cargo bisect-rustc --start=2018-05-07 --end=2018-08-04
```

เครื่องมือจะสั่งรัน `cargo build` ในโปรเจกต์และตรวจสอบว่าบิลด์ผ่านหรือไม่ จากนั้นจะทำการค้นหาแบบไบนารีระหว่างช่วง start ถึง end เพื่อชี้ชัดลงไปว่าจุดที่เกิดรีเกรสชันอยู่ที่ใดกันแน่

> **หมายเหตุ**: คุณสามารถใช้แฟล็ก [`--regress`] เพื่อกำหนดเกณฑ์การเกิดรีเกรสชันอื่นๆ ได้ เช่น `--regress=ice` สำหรับกรณีข้อผิดพลาดภายในคอมไพเลอร์ (ICE)

[`--regress`]: usage.md#การตรวจสอบรีเกรสชัน

> **หมายเหตุ**: นอกเหนือจากวันที่แล้ว คุณยังสามารถระบุขอบเขตด้วยเวอร์ชัน stable หรือ git commit hash ได้อีกด้วย ดูรายละเอียดเพิ่มเติมเกี่ยวกับการตั้งค่าตัวเลือกเหล่านี้ได้ที่บท [ขอบเขตการไบเซกต์]

[ขอบเขตการไบเซกต์]: boundaries.md

ในตัวอย่างนี้ เพียงไม่กี่ขั้นตอน เครื่องมือจะพบว่าโค้ดเริ่มมีปัญหาตั้งแต่เวอร์ชัน `nightly-2018-07-30`

หากรีเกรสชันนั้นเพิ่งเกิดขึ้นไม่นานนี้ (ยังอยู่ในช่วง 167 วัน) เครื่องมือจะพิมพ์รายชื่อ PR ทั้งหมดที่ถูกคอมมิตในวันดังกล่าวออกมา แต่เนื่องจากตัวอย่างนี้เป็นรีเกรสชันที่เก่ามาก เราจึงต้องตรวจสอบ git log ด้วยตนเองเพื่อดูว่ามี PR ใดบ้างที่ถูก merge เข้ามา

และหาก nightly ที่พบอยู่ในช่วง 167 วันล่าสุด `cargo-bisect-rustc` ก็จะเริ่มขั้นตอนไบเซกต์ย่อยระหว่างแต่ละ PR เหล่านั้นให้ทันที

หลังจากได้รายชื่อ PR ที่เข้าข่ายเป็นไปได้แล้ว คุณสามารถเข้าไปตรวจสอบเนื้อหาในแต่ละ PR เพื่อดูว่าตัวใดน่าจะเป็นสาเหตุ ในกรณีนี้ อาการ ICE เกิดขึ้นในขั้นตอน MIR const propagation ดังนั้น PR #51361 จึงเป็นผู้ต้องสงสัยที่มีแนวโน้มมากที่สุด เนื่องจากมีการปรับแก้โค้ดส่วนการประเมินค่าคงที่ (const evaluation)

## การทดสอบแบบอินเทอร์แอกทีฟ

บางครั้งการดูแค่ผล 'ผ่าน/ล้มเหลว' ของ `cargo build` อาจไม่ตรงกับสิ่งที่คุณต้องการสืบหา เช่น ปัญหาอาจเป็นเรื่องข้อความแสดงข้อผิดพลาด (error message) ที่เปลี่ยนไป ส่งผลให้ทั้งเวอร์ชันที่ 'ดี' และเวอร์ชันที่ 'มีปัญหา' ต่างก็คอมไพล์ไม่ผ่านทั้งคู่ เพียงแต่แสดงข้อความคนละแบบ หรือในบางกรณี โค้ดที่เคยคอมไพล์ไม่ผ่าน กลับกลายเป็นคอมไพล์ผ่านอย่างไม่ถูกต้อง

คุณสามารถเปิดใช้โหมดอินเทอร์แอกทีฟด้วยแฟล็ก `--prompt` เพื่อตรวจสอบผลลัพธ์การบิลด์ในแต่ละรอบด้วยสายตาตนเอง แล้วบอกกับ `cargo-bisect-rustc` ว่าผลลัพธ์รอบนั้น 'ดี' หรือ 'มีปัญหา'

ลองดูตัวอย่างจาก [issue #55036] ซึ่งเป็นกรณีที่ข้อความ error message มีการเปลี่ยนแปลง:

ในไฟล์ `Cargo.toml` ให้ลบฟิลด์ `edition` ออก (ตัวอย่างนี้เกิดขึ้นก่อนที่จะมีระบบ editions ใน Rust)

`src/main.rs`:
```rust
struct Foo {
    bar: i32
}

trait Baz {
    fn f(Foo { bar }: Foo) {}
}

fn main() {}
```

ในอดีต โค้ดนี้เคยแสดงข้อความผิดพลาดที่ไม่ชัดเจน ต่อมาได้รับการปรับปรุงให้แสดงข้อความที่เข้าใจง่ายขึ้น (เพิ่มรหัส E0642 ใน PR #53051) แต่แล้วข้อความแจ้งเตือนที่ปรับปรุงแล้วนั้นกลับหายไปอย่างไร้ร่องรอย (บน edition 2015)
มาลองค้นหากันว่าข้อความดังกล่าวหายไปที่จุดไหน! ให้ระบุช่วงระหว่างวันที่เพิ่มฟีเจอร์นี้ กับวันที่ทราบว่าเกิดปัญหา:

```sh
cargo bisect-rustc --prompt \
    --start=2018-08-14 \
    --end=2018-10-11
```

ในแต่ละขั้นตอน `cargo-bisect-rustc` จะแสดงผลลัพธ์และสอบถามคุณ:

```text
nightly-2018-08-14 finished with exit code Some(101).
please select an action to take:
> mark regressed
  mark baseline
  retry
```

ให้เลือก `mark baseline` เมื่อพบผลลัพธ์ที่แสดงข้อความแจ้งเตือน E0642 ที่ชัดเจน และเลือก `mark regressed` สำหรับรอบที่แสดงข้อผิดพลาด token error ที่แย่กว่า
เพียงไม่นาน เราจะพบว่าเกิดรีเกรสชันขึ้นในเวอร์ชัน `nightly-2018-10-11`
โดยผู้ต้องสงสัยที่มีโอกาสมากที่สุดคือ PR #54457 ซึ่งเป็นโรลอัป PR
ปกติแล้วการไล่ดูคอมมิตย่อยภายในโรลอัปเพื่อหาตัวการที่แท้จริงไม่ใช่เรื่องยาก ซึ่งในตัวอย่างนี้ก็คือ PR #54415 ที่มีการแก้ไขโค้ดส่วนการแยกวิเคราะห์พารามิเตอร์ของฟังก์ชัน (function parameter parsing)

## การทดสอบด้วยสคริปต์

การใช้ตัวเลือก `--script` ช่วยให้คุณทำอะไรได้มากกว่าแค่การรัน `cargo build` เช่น คุณอาจจำเป็นต้องสั่งรัน cargo หลายรอบ, เรียกคำสั่ง `rustc` โดยตรง, หรือต้องการใช้ `grep` กรองข้อความจาก output โดยอัตโนมัติ ความเป็นไปได้จึงไร้ขีดจำกัด!
เพียงเขียนเชลล์สคริปต์สั้นๆ ให้คืนค่า exit code 0 สำหรับสถานะ baseline และคืนค่าไม่เท่ากับ 0 สำหรับสถานะรีเกรสชัน ตัวอย่างเช่น ขั้นตอนอินเทอร์แอกทีฟในหัวข้อก่อนหน้า สามารถปรับให้ทำงานแบบอัตโนมัติทั้งหมดได้ด้วยสคริปต์นี้:

`test.sh`:
```sh
#!/bin/sh

# Fail if we no longer get a `E0642` error:
cargo check 2>&1 | grep E0642
```

จากนั้นสั่งรัน:

```sh
cargo bisect-rustc --script=./test.sh \
    --start=2018-08-14 \
    --end=2018-10-11
```

## ข้อความไบเซกต์ที่กำหนดเอง

*มีให้ใช้งานตั้งแต่ v0.6.9*

คุณสามารถกำหนดข้อความแสดงผลเองได้ระหว่างการไบเซกต์รีเกรสชัน โดยฟีเจอร์นี้ได้แรงบันดาลใจมาจาก git-bisect ซึ่งการใช้ `term-new` และ `term-old` จะช่วยให้คุณระบุข้อความเฉพาะเพื่อบอกว่าการบิลด์รอบนั้นตรงกับเงื่อนไขที่กำลังค้นหาหรือไม่

ตัวอย่าง:
```sh
cargo bisect-rustc \
    --start=2018-08-14 \
    --end=2018-10-11 \
    --term-old "No, this build did not reproduce the regression, compile successful" \
    --term-new "Yes, this build reproduces the regression, compile error"
```

กล่าวอีกนัยหนึ่งคือ `--term-old` จะแสดงสำหรับคอมไพเลอร์เวอร์ชันเก่าที่ **ไม่พบ** รีเกรสชัน ส่วน `--term-new` จะแสดงสำหรับคอมไพเลอร์เวอร์ชันใหม่ที่ **พบ** รีเกรสชัน

สิ่งที่ถือว่าเป็น "รีเกรสชัน" นั้นถูกกำหนดโดยตัวเลือก CLI [`--regress`](usage.html#การตรวจสอบรีเกรสชัน) โดยค่าเริ่มต้น รีเกรสชันคือการคอมไพล์แล้วเกิดข้อผิดพลาด (ซึ่งเทียบเท่ากับ `--term-new`) แต่หากคุณกลับนิยามของคำว่ารีเกรสชันด้วย `--regress=success` รีเกรสชันจะกลายเป็นการคอมไพล์ที่สำเร็จแทน (ซึ่งก็เทียบเท่ากับ `--term-new` เช่นกัน)

ระบบมีข้อความเริ่มต้นตามการตั้งค่า `--regress` ที่ใช้งานอยู่แล้ว แต่การกำหนดข้อความเองจะมีประโยชน์สูงสุดเมื่อใช้ร่วมกับ [การเขียนสคริปต์](#การทดสอบดวยสคริปต) ตัวอย่างเช่น ในบท [การเปลี่ยนแปลงเอกสารประกอบ](examples/doc-change.md) ข้อความที่กำหนดเองจะช่วยสื่อสารผลลัพธ์ของสคริปต์ได้ชัดเจนยิ่งขึ้น ว่าสคริปต์ค้นพบสิ่งที่ต้องการในเอกสารหรือไม่
