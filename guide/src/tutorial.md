# บทช่วยสอน

`cargo-bisect-rustc` ทำงานโดยการบิลด์โปรเจกต์ Cargo และตรวจสอบว่าการบิลด์สำเร็จหรือล้มเหลว
บทช่วยสอนนี้จะพาคุณเดินผ่านตัวอย่างของกระบวนการนี้

## การค้นหารีเกรสชัน

สร้างโปรเจกต์ cargo ที่จำลองรีเกรสชันได้
ลองใช้ [issue #53157] เป็นตัวอย่าง:

```sh
cargo new foo
cd foo
```

แก้ไข `src/main.rs` ด้วยตัวอย่างจาก issue:

```rust
macro_rules! m {
    () => {{
        fn f(_: impl Sized) {}
        f
    }}
}

fn main() {
    fn f() -> impl Sized {};
    m!()(f());
}
```

เนื่องจากเรากำลังทดสอบรีเกรสชันเก่า ให้แก้ไข `Cargo.toml` เพื่อลบฟิลด์ `edition = "2021"` ซึ่งเวอร์ชันเหล่านี้ไม่รองรับ

จากนั้นรัน `cargo bisect-rustc --end=2018-08-04`

เราต้องระบุจุดสิ้นสุด (end point) สำหรับตัวอย่างนี้โดยเฉพาะ เพราะเป็นรีเกรสชันเก่าที่ถูกแก้ไขบน nightly ล่าสุดแล้ว
เราสามารถระบุจุดเริ่มต้น (start point) ได้ด้วยถ้าเรารู้จักจุดนั้น
วิธีนั้นจะทำให้เร็วขึ้นเพราะไม่ต้องสแกนหาจุดเริ่มต้น เช่น:

```sh
cargo bisect-rustc --start=2018-05-07 --end=2018-08-04
```

เครื่องมือจะรัน `cargo build` ในโปรเจกต์และตรวจสอบว่าล้มเหลวหรือไม่
จากนั้นจะทำการค้นหาแบบไบนารีระหว่างช่วง start ถึง end เพื่อหาจุดที่เกิดรีเกรสชันอย่างแม่นยำ

> **หมายเหตุ**: คุณยังสามารถใช้ตัวเลือก [`--regress`] เพื่อระบุเกณฑ์รีเกรสชันทั่วไปอื่น ๆ ได้ เช่น `--regress=ice` สำหรับข้อผิดพลาดภายในคอมไพเลอร์

[`--regress`]: usage.md#การตรวจสอบรีเกรสชัน

> **หมายเหตุ**: วิธีอื่น ๆ ในการระบุขอบเขต ได้แก่ เวอร์ชัน stable และ git commit hashes ดูบท [ขอบเขตการไบเซกต์] สำหรับรายละเอียดเพิ่มเติมเกี่ยวกับการตั้งค่าตัวเลือกเหล่านี้

[ขอบเขตการไบเซกต์]: boundaries.md

ในตัวอย่างของเรา ในไม่กี่ขั้นตอน เราจะพบว่ามันหยุดทำงานที่ `nightly-2018-07-30`

ถ้ารีเกรสชันเกิดขึ้นเร็วพอ เครื่องมือจะพิมพ์รายการ PR ที่ถูกคอมมิตในวันนั้น
ในตัวอย่างนี้ รีเกรสชันเก่าเกินไป เราจึงต้องตรวจสอบ git log ด้วยตัวเองเพื่อดูว่า PR ใดถูก merge บ้าง

ถ้า nightly อยู่ในช่วง 167 วันล่าสุด `cargo-bisect-rustc` จะเริ่มไบเซกต์ PR แต่ละตัวเหล่านั้น

หลังจากพบผู้ต้องสงสัยที่เป็นไปได้ คุณสามารถไปตรวจสอบ PR เหล่านั้นเพื่อดูว่าตัวไหนน่าจะเป็นสาเหตุ
ในกรณีนี้ เนื่องจาก ICE เกิดขึ้นในขั้นตอน MIR const propagation (การแพร่ค่าคงที่บน MIR) และ #51361 คือตัวเลือกที่น่าจะเป็นไปได้เพราะมันแก้ไขการประเมินค่าคงที่ (const evaluation)

## การทดสอบแบบอินเทอร์แอกทีฟ

ผ่าน/ล้มเหลวของ `cargo build` อาจไม่ใช่สิ่งที่คุณต้องการ
บางทีปัญหาคือข้อความแสดงข้อผิดพลาดเปลี่ยนไป ทำให้เวอร์ชัน "ดี" และ "แย่" ต่างก็คอมไพล์ไม่ผ่าน แต่ด้วยข้อความที่ต่างกัน
หรือบางอย่างที่เคยล้มเหลว ตอนนี้กลับผ่านอย่างผิดพลาด
คุณสามารถใช้ฟีเจอร์อินเทอร์แอกทีฟกับตัวเลือก `--prompt` เพื่อตรวจสอบผลการบิลด์ด้วยตา และบอก `cargo-bisect-rustc` ว่าอันไหน "ดี" และอันไหน "แย่"
ลองใช้ [issue #55036] เป็นตัวอย่างที่ข้อความแสดงข้อผิดพลาดเปลี่ยนไป:

ใน `Cargo.toml` ให้ลบฟิลด์ `edition` (ตัวอย่างนี้เกิดขึ้นก่อนที่จะมี editions)

`src/main.rs`:
```rust
struct Foo {
    bar: i32
}

trait Baz {
    fn f(Foo { bar }: Foo) {}
}

fn main() {}
```

ในอดีตสิ่งนี้เคยแสดงข้อผิดพลาดที่แย่ ต่อมาถูกอัปเดตให้แสดงข้อผิดพลาดที่ดี (E0642 ถูกเพิ่มใน #53051) แต่แล้วข้อผิดพลาดที่ดีนั้นก็หายไปที่ไหนสักแห่ง (บน edition 2015)
มาหากันว่ามันหายไปที่ไหน!
ใช้ช่วงระหว่างจุดที่มันถูกเพิ่มกับจุดที่เรารู้ว่ามันล้มเหลว:

```sh
cargo bisect-rustc --prompt \
    --start=2018-08-14 \
    --end=2018-10-11
```

ในแต่ละขั้นตอน `cargo-bisect-rustc` จะแสดงผลลัพธ์และถามคุณ:

```text
nightly-2018-08-14 finished with exit code Some(101).
please select an action to take:
> mark regressed
  mark baseline
  retry
```

เลือก `mark baseline` สำหรับเวอร์ชันที่มีข้อความ E0642 ที่ดี และเลือก `mark regressed` สำหรับเวอร์ชันที่มีข้อผิดพลาดแบบ token ที่แย่กว่า
ไม่นานเราก็พบว่ามันเกิดรีเกรสชันที่ nightly-2018-10-11
ผู้ต้องสงสัยที่น่าจะเป็นไปได้มากที่สุดคือ #54457 ซึ่งเป็นโรลอัป PR
ปกติแล้วการไล่ดูคอมมิตเพื่อหาผู้ร้ายที่น่าจะเป็นไปได้ก็ไม่ยากนัก
ในตัวอย่างนี้จริง ๆ แล้ว #54415 แก้การแยกวิเคราะห์พารามิเตอร์ของฟังก์ชัน (function parameter parsing)

## การทดสอบด้วยสคริปต์

การใช้ตัวเลือก `--script` ทำให้คุณทำอะไรที่ซับซ้อนกว่าแค่ `cargo build`
บางทีคุณต้องรัน cargo หลายครั้ง หรือเรียก `rustc` โดยตรง หรือต้องการ grep ผ่านผลลัพธ์โดยอัตโนมัติ
ความเป็นไปได้ไม่มีที่สิ้นสุด!
เพียงเขียนสคริปต์เชลล์เล็ก ๆ ที่คืนค่า exit code 0 สำหรับ baseline และคืนค่าไม่ใช่ 0 สำหรับรีเกรสชัน
ตัวอย่างเช่น เซสชันอินเทอร์แอกทีฟก่อนหน้านี้สามารถทำอัตโนมัติได้โดยไม่ต้องแตะมือด้วยสคริปต์นี้:

`test.sh`:
```sh
#!/bin/sh

# Fail if we no longer get a `E0642` error:
cargo check 2>&1 | grep E0642
```

จากนั้นรัน:

```sh
cargo bisect-rustc --script=./test.sh \
    --start=2018-08-14 \
    --end=2018-10-11
```

## ข้อความไบเซกต์ที่กำหนดเอง

*มีให้ใช้งานตั้งแต่ v0.6.9*

คุณสามารถเพิ่มข้อความที่กำหนดเองได้เมื่อไบเซกต์รีเกรสชัน โดยได้แรงบันดาลใจจาก git-bisect ด้วย `term-new` และ `term-old` คุณสามารถตั้งข้อความที่กำหนดเองเพื่อระบุว่ารีเกรสชันตรงกับเงื่อนไขที่กำหนดโดยการไบเซกต์หรือไม่

ตัวอย่าง:
```sh
cargo bisect-rustc \
    --start=2018-08-14 \
    --end=2018-10-11 \
    --term-old "No, this build did not reproduce the regression, compile successful" \
    --term-new "Yes, this build reproduces the regression, compile error"
```

กล่าวอีกนัยหนึ่ง `--term-old` จะแสดงสำหรับคอมไพเลอร์รุ่นเก่าที่ **ไม่** แสดงรีเกรสชัน ส่วน `--term-new` สำหรับคอมไพเลอร์รุ่นใหม่ที่แสดงรีเกรสชัน

สิ่งที่ถือว่าเป็น "รีเกรสชัน" นั้นถูกกำหนดโดยตัวเลือก CLI [`--regress`](usage.html#การตรวจสอบรีเกรสชัน) โดยค่าเริ่มต้น รีเกรสชันคือคอมไพล์ที่เกิดข้อผิดพลาด (ซึ่งเทียบเท่ากับ `--term-new`) หากคุณกลับนิยามของ "รีเกรสชัน" ด้วย `--regress=success` แล้ว รีเกรสชันจะกลายเป็นการคอมไพล์ที่สำเร็จ (ซึ่งก็เทียบเท่ากับ `--term-new` เช่นกัน)

มีข้อความเริ่มต้นตามการตั้งค่า `--regress` ปัจจุบัน การปรับแต่งข้อความเป็นประโยชน์ที่สุดเมื่อใช้ [การเขียนสคริปต์](#การทดสอบดวยสคริปต) ตัวอย่างเช่น ในตัวอย่าง [การเปลี่ยนแปลงเอกสารประกอบ](examples/doc-change.md) ข้อความที่กำหนดเองสามารถสื่อผลลัพธ์ของสคริปต์ได้ชัดเจนขึ้นว่าสคริปต์เจอสิ่งที่กำลังค้นหาหรือไม่
